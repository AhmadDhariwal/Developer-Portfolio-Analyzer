## Audit and corrections

- Generation previously coalesced only within one process. It now acquires a server-time Mongo lease keyed by owner/week. A token/expiration fence executes inside the existing report/notification transaction. Expired workers cannot overwrite a successor. The week used for the lease and persistence is captured once. Local coalescing remains an optimization, not the authority.
- The scheduler previously repeatedly selected only the first configured batch. It now traverses active, opted-in users with bounded `_id` keyset pages and existing bounded concurrency. Transactional weekly checkpoints advance only after a successful page. A failed page is retried by the dedicated worker sweep; already completed weeks are skipped. Restart replay uses report identity and existing smart-skip/email lifecycle rules.
- Added `backend/src/workers/weeklyReports.js`. It explicitly requires scheduler enablement, performs startup catchup, schedules the existing cron and polls pending work/email once a minute. API deployments can set `WEEKLY_REPORT_PROCESS_ROLE=api` to disable their generation scheduler. If inline scheduling is retained, Mongo leases coordinate accidental replicas. No production deployment settings were changed.
- Week calculations previously used host-local Date operations even when cron had a different configured timezone. The existing Temporal dependency now calculates Monday boundaries and prior weeks in `WEEKLY_REPORT_TIMEZONE`, including DST. The default remains the server timezone. Historical report windows are not migrated.
- The schema discarded the ninth source (`learning`) and stale-source warnings already emitted by generation. Approved optional fields now retain these and freshness for every source. Missing historical metadata remains missing; no backfill was performed. Interview freshness now uses the most recently updated session.
- A first saved report previously compared current score evidence with an invented zero baseline. It now establishes a baseline and suppresses unsupported score/coverage deltas. The weighted score formula remains GitHub 30%, resume 25%, Sprint completion 20%, interview 15%, skill coverage 10%.
- AI output previously passed shape-only checks, allowing invented achievements. AI is now restricted to selecting/reordering the supplied deterministic narrative statements, with exact factual validation and deterministic fallback. Scores, risk, readiness, sources, snapshots and hashes remain server-derived. This is deliberately conservative; arbitrary AI paraphrases are rejected. Existing AI budget/provider admission controls remain in use; no provider quota is bypassed.
- Frontend invalidation previously cleared maps but left transports alive, allowing stale responses to fill later account caches. Pending reads now cancel on invalidation; generation responses are checked against the captured owner/context and invalidation epoch. Dashboard coalescing includes owner identity. Component teardown cancels subscriptions and releases busy states; regeneration errors retain the saved report.
- UI now has a score ring with an accessible meter, saved-week trend navigation, evidence source visibility including unavailable sources, clearer readiness language, responsive history and shared semantic theme surfaces. Fixed malformed history punctuation and light-theme contrast found during screenshot review. Added focus treatment, busy/error semantics and reduced-motion support. Readiness is explicitly a planning indicator, not a hiring probability.

## Email and crash policy

Existing delivery claims remain atomic and owner/preference checked immediately before sending. They use bounded attempts/backoff and a processing lease. An ambiguous timeout/disconnect or expired processing lease becomes `uncertain`, preventing automatic resend/provider fallback. Definite pre-delivery rejection can retry. A newer report can be saved while an earlier email is uncertain; pending content coalesces without erasing that uncertainty. Operator reconciliation against provider delivery evidence is required before authorizing another send. No live emails were sent in this task.
