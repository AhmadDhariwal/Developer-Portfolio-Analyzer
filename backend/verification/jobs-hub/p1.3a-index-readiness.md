# P1.3A candidate discovery index readiness

No new index or data migration is required by this change. No production indexes
were changed. The local explain evidence uses the repository's existing indexes.

The discovery query needs a MongoDB replica set for its read-only snapshot and
the aggregation operators used by the installed MongoDB 8.2 test server. Verify
target-server capabilities before an independently approved rollout.

## Read-only deployment check

Inspect indexes on the target database using the usual authorized maintenance
connection. These commands are inspection instructions, not commands run by this
task:

```javascript
db.users.getIndexes();
db.analyses.getIndexes();
db.resumeanalyses.getIndexes();
db.publicprofiles.getIndexes();
db.careersprints.getIndexes();
db.weeklyreports.getIndexes();
db.candidates.getIndexes();
```

The declared User eligibility indexes are:

| Collection | Existing key pattern                                               |
| ---------- | ------------------------------------------------------------------ |
| users      | `{ isPublic: 1, role: 1, isActive: 1, _id: 1 }`                    |
| users      | `{ organizationId: 1, isPublic: 1, role: 1, isActive: 1, _id: 1 }` |

Each evidence collection above also needs an existing index whose first key is
`userId`. A compound prefix is sufficient for the equality joins. Existing
analysis and resume indexes are used as prefixes; their exact chosen names can
vary with the planner and data distribution.

If any declared baseline index is missing, prepare a separate approved index
repair using the exact model key pattern and options. Do not call `syncIndexes`,
drop indexes, create speculative computed-score indexes, or add a redundant
`userId` index when a suitable prefix already exists. Validate the repair on a
disposable copy and review the plan and write load before any production action.

## Explain and workload verification

Run the focused disposable fixture from `backend`:

```powershell
node --test src/tests/recruiter/candidateDiscovery.integration.test.js
```

The test reports a small join probe and the complete 2,205-candidate pipeline.
Verify SBE equality joins (`EQ_LOOKUP`) for all six evidence sources, bounded
returned page size, and exact totals after all filters. The planner may choose
indexed loop joins or hash joins for small foreign tables; do not force an index
when a measured hash join is cheaper. The test rejects unindexed nested loops. A broad
public query may examine all eligible Users: exact counts and derived-score
sorting require processing that eligible population. English name collation and
computed sort keys mean that an index-backed final sort is not claimed.

The original correlated `$lookup` pipelines used indexes but exceeded the
15-second query budget. Adjacent equality joins removed that per-candidate
subquery-planning cost. This was a query-shape issue; the evidence did not justify
adding indexes. The retained P1.3A report contains measured local timings and
selected index names. The incomplete old 1,000-user sample is not an equivalent
performance workload to the complete new population.

## Operating limits and P1.3B preparation

- Page results are limited to 240. Offset skips above 50,000 require the signed
  continuation cursor; the eligible population and exact count are not capped.
- Aggregations have a 15-second time budget and use bounded response facets.
  Time-budget errors return 503, never an empty successful page.
- Source histories are joined inside MongoDB and collapsed there. Only one
  selected record per source and a rolled-up legacy alias are hydrated for each
  returned candidate. Very large histories for a single User remain subject to
  MongoDB document and aggregation memory limits. No history is silently truncated
  to change a score. Measure those histories before increasing production load.
- P1.3B may need an explicitly versioned, transactionally maintained source-head
  or assessment projection for larger workloads. Its ownership, invalidation,
  freshness, consent withdrawal, backfill and parity contracts must be designed
  first. This phase adds no projection cache or worker.
- Duplicate Analysis/PublicProfile source rows need a consistent repair policy
  across consumers. Discovery chooses the newest `_id`; dated resume, sprint and
  weekly sources use their existing date semantics with deterministic ID ties.
  Existing matching consumers retain their prior selectors and formulas.

No application evidence, team evaluation permission or application lifecycle
linkage is changed by an index-readiness check.
