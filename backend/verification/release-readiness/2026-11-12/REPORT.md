## Scenario Simulator: highest unresolved performance issue

The retained final trace records **5,915/6,000 successful responses and 85 Redis quota 503s (1.42%)** during a direct 60-second, 100-RPS burst. A separate direct run had 49/6,000 503s (0.82%); the preceding full protocol burst had 58/6,000 (0.97%). The accepted unexpected-5xx target is `<0.5%`; the trace run clearly fails. All traced errors were `Redis command timed out` at the existing 150 ms deadline. Redis later delivered each matching reply; the write dispatch and reply were late. Redis Lua mean execution was 70.69 microseconds and the longest SLOWLOG entry 9.032 ms, so Redis script execution is not the measured bottleneck. Both workers had overlapping event-loop pauses up to 232/246 ms. The run used Windows/WSL1, Node 24.19, two workers and Redis 7.2.11. It does not isolate a host scheduler stall from a synchronous application callback.

Run one deployment-equivalent, low-observer diagnostic cycle before considering code changes:

1. Pin the exact candidate commit, Node version, Redis version/config/TLS, Mongo driver, pool settings, CPU/memory limits, proxy/load balancer and autoscaling/instance count from the intended deployment. Use native Linux instances with the enforced target topology (the acceptance charter calls for two 2-vCPU/1-GB workers); publish actual effective limits and container CPU throttling.
2. Reproduce on two independent API processes using the real shared Redis path, one new synthetic account set and no application fallback. Run a 60-second 100-RPS/6,000-request burst, the 15-minute 20-RPS steady phase, source/Mongo fault phases and 60-minute 20-RPS soak from `FINAL-ACCEPTANCE.md`. Keep intentional quota rejections separate from unexpected 5xx and preserve the original latency/resource limits.
3. During a capacity run, collect only low-cost per-process `monitorEventLoopDelay`/event-loop utilization, CPU throttling/process CPU, GC pause counts, Redis PING RTT, client socket enqueue/write-callback/reply timings, client pending/waiting queues and Redis SLOWLOG. Collect the verbose Redis MONITOR/socket trace in a separate diagnostic reproduction so instrumentation does not itself perturb the capacity result.
4. Keep both run results, all statuses and latency histograms, per-worker distributions, server/driver/pool telemetry, dependency versions, and fault timeline. Pass only if unexpected 5xx stays below the published `<0.5%` gate in every accepted phase, the burst no longer reproduces 150-ms healthy-Redis timeouts, and all existing p95/p99/resource/fan-out/queue-drain checks pass. Intentional fail-closed 503s in injected dependency failure remain separately classified.

If native Linux still reproduces the delay, profile event-loop callback stacks and correlate client socket callbacks with the kernel/network and Redis node before changing queue limits, deadlines, scoring, request concurrency or fail-open policy. The existing 2,000-command queue bound and fail-closed quota behavior should remain intact during diagnosis.

## Security, configuration, data and operations

**Dependency advisories.** Installed direct versions are Angular 21.2.1, Multer 2.1.1 and Axios 1.13.6. Current GitHub advisories identify Angular compiler/core `<21.2.4` for i18n-sensitive untrusted attribute bindings; the checkout search found no `i18n-href/src/action/formaction` bindings, so the published exploit precondition is not demonstrated here, but the installed version is vulnerable and needs a coordinated Angular patch. Multer `<2.3.0` has high-severity crafted multipart field DoS; the current 2.1.1 falls in range and upload routes use Multer. Current upload `fileFilter`s are synchronous, so the separate Oct-2026 async-filter advisory's exact condition was not found. Upgrade to a patched supported release (the later pending async-filter advisory specifies 2.5.0), then regression-test all authenticated upload paths and body/field limits. Axios advisories published Sep-2026 include high findings affecting `>=1.13.0`, patched at `>=1.20.0`, for Node HTTP/2; this source search found no explicit `httpVersion: 2` usage. Update/audit the full dependency graph and exercise outbound URL/proxy policy before treating it as cleared. Advisories: [Angular GHSA-g93w-mfhg-p222](https://github.com/angular/angular/security/advisories/GHSA-g93w-mfhg-p222), [Multer GHSA-535w-7cp7-47q4](https://github.com/expressjs/multer/security/advisories/GHSA-535w-7cp7-47q4), [Multer GHSA-q7qp-rjg7-q26m](https://github.com/expressjs/multer/security/advisories/GHSA-q7qp-rjg7-q26m), [Axios GHSA-542g-h47m-68v8](https://github.com/axios/axios/security/advisories/GHSA-542g-h47m-68v8), [Axios GHSA-3pq3-5fj3-cg6v](https://github.com/axios/axios/security/advisories/GHSA-3pq3-5fj3-cg6v). These are version-range findings; they do not claim every advisory is reachable through this application. `npm audit` could not reach `registry.npmjs.org` (DNS `ENOTFOUND`) in this environment. The offline `--omit=dev` command reported zero, but is not a full, current advisory audit. `npm ls --depth=0` passed for both installed trees. No complete current full-tree advisory result is available.

**Credential incident.** The retained Recommendations production report says a Google API key appeared in unrelated process-command diagnostic output; it says the value was not stored in the report and recommends revocation/rotation. This audit did not inspect or expose secret values and cannot confirm whether the key was rotated. Treat revocation, rotation, usage review and affected-environment inventory as a release blocker; do not place key material in this report.

**Configuration and deployment.** No Dockerfile, Compose, Render/Heroku/Fly manifest, Procfile or GitHub Actions workflow is present in the tracked file inventory. There is no checked-in deployment-equivalent topology or repeatable CI release gate. `backend/index.js` starts integrations, jobs, news, notifications, course maintenance and interview schedulers alongside the API in normal mode; Weekly Reports has `WEEKLY_REPORT_PROCESS_ROLE=api` as a special scheduler switch. Local process-level starts and service-specific leases are not evidence of a clean API/worker separation or crash-safe multi-replica deployment. Verify every scheduler's distributed lease, leader/restart behavior, graceful shutdown, readiness and duplicate execution under the real role topology.

**MongoDB and Redis.** Mongoose models declare substantial compound and TTL indexes; module-local reports show disposable explain plans (for example Recommendation examines 20 keys/docs for 20 results, and Scenario verifies owned-history/cursor indexes). Dashboard's synthetic query plans and 5,000-row integration aggregate are useful but do not establish deployed collection cardinality, exact indexes, write amplification or pool pressure. No authorized staging Mongo topology/index inventory is configured. Do not apply further speculative indexes; capture `listIndexes` and representative `explain('executionStats')` plus write/pool measurements on staging first. Redis is optional for broad caches with process-memory fallbacks, while quotas/governance paths depend on shared authority and some fail closed. Integrations' retained provider acceptance says the configured Upstash PING did not become ready; root cause was unresolved. The Scenario 150-ms shared Redis timeout is independently failing. Stage live TLS/ACL, latency, reconnect/failover and cross-process behavior before release. No Redis manifests/hosted topology are in source control.

**Caching and data consistency.** Dashboard now uses a bounded optimistic source snapshot and owner/profile/resume scope. Integration, Recommendation and Skill Gap reports describe revision-aware caches and invalidation; Redis or in-process maps remain optimizations, with Mongo/snapshot ownership authoritative in several paths. However, no single end-to-end test changes GitHub source and verifies invalidation through Skill Gap → Recommendations → Sprint → Dashboard → a newly generated Weekly Report across two application processes. Cross-module focused tests cover subsets; they do not establish this exact chain. Report consumers must keep provenance/version and missing-versus-zero semantics intact during branch reconciliation.

**Observability and data lifecycle.** Dashboard latency alert now uses 1,800 ms against a millisecond histogram and has a focused rule regression; Promtool/live alert evaluation is absent. The configured error alert fires above 20% for five minutes, a threshold whose usefulness against the service SLO has not been established. Weekly report and Scenario logs/metrics are not shown against a live fleet. AIVersion history has no TTL per Recommendations audit; Public Portfolio retains public legacy filesystem image URL behavior after unpublishing. Approve retention, deletion, backup restore, PII/key handling and alert ownership before launch. No backup/restore drill is represented in the module reports inspected.
