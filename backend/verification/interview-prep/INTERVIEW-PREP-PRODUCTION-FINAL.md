## Architecture findings and fixes

The existing routes use JWT `protect` before Interview Prep handlers. Controllers resolve the saved career profile and the existing compatible-current Resume/Skill Gap evidence resolver. Services normalize technologies, select verified seed/database content, validate answers, and call provider adapters only for explicit generation/enrichment. The repository owns public approval/privacy filters and atomic trust-protected upserts. MongoDB stores the bank and private session snapshots; Redis and bounded process memory accelerate reads.

- **Technology and filters:** Java/JavaScript, React/React Native, Node/Next, C#/C++ and unknown topics retain separate canonical identities. AngularJS incorrectly aliased modern Angular; it now stays isolated as `angularjs`. Top Questions previously ignored category/source despite caching those inputs. The frontend also omitted these filters from Top/search, and search omitted source from its backend cache identity. All those paths now propagate and apply the filters. Invalid category/source values receive 400 responses.
- **Ranking and pagination:** All Questions retains the stable Mongo sort `qualityScore DESC, rankScore DESC, createdAt DESC, _id ASC`; usage updates cannot reorder these pages. Text-score pagination retains its `_id` tie-breaker. Existing bounded candidate matching, unique topic/question/seed indexes and duplicate-key retries remain. No speculative replacement of the ranking engine was made.
- **Provenance and quality:** Verified seeds, generated answers and structured enrichment retain separate provenance. Enrichment records its original source and an unverified status and cannot overwrite verified/prebuilt seeds, including through a stale repository update. Existing seven-section schema, placeholder/contradiction/topic/comparison checks and pending-review scraped content remain. Structural approval is not factual verification. Generated bank content receives a content version when none is supplied; response identities and historical snapshots carry stable identity/content hashes.
- **Invalidation:** Existing memory → Redis → Mongo/seed reads, 30-second Interview memory TTL, 2,000-entry memory bound, Redis TTL-safe promotion, shared topic/global revisions and recovery namespaces remain. Repository inserts/updates now invalidate their topic, including enrichment updates, rather than relying solely on inserted-count checks in callers. Question, search and private custom cache keys include the applicable topic, filters, pagination, mode, revision and owner. Custom response caches never share session IDs across owners.
- **Provider governance:** `interviewCoordination` is a dedicated Mongo collection for atomic user rate reservations, a module-wide AI minute quota, bounded global AI slots, identical-prompt leases, fenced result publication and short failure cooldowns. It works independently of Redis and fails closed on unavailable admission storage. Default limits: custom 20/search 60/generate 30 per user per 10-minute fixed window; 4 Interview AI slots; 60 Interview AI attempts per minute. Operators can set bounded existing rate variables and the new `INTERVIEW_AI_MAX_CONCURRENCY` and `INTERVIEW_AI_MAX_PER_MINUTE` variables identically on all workers. These are Interview module limits, not promises about unrelated modules or a provider account's purchased quota.
- **Single flight:** Provider identity includes the complete prompt, preferred model and schema version. Identical requests across users/workers share a schema-validated transport result for 60 seconds; it contains no session/owner identifier and is never a public bank record. User history is still stored and read separately. Failed results carry only a failure marker for 3 seconds. Pending leases/slots expire after 15 seconds; token-conditional publication and release fence stale owners. Polling is bounded to 6.3 seconds. Expiry is checked explicitly; TTL cleanup timing is not used for correctness. Exactly-once external billing after a process crash cannot be guaranteed without provider-side idempotency.
- **AI budget and fallback:** The 6,200 ms provider timeout remains, with the existing 6,500 ms service safety deadline. Interview calls allow one provider attempt and zero application retries inside that budget, preserving safe verified/no-answer fallbacks. The coordinator sends an abort signal on its deadline; the existing provider manager handles abortable transports. Raw Interview output bypasses the general AI response cache so malformed JSON/schema output is not cached there. Shared transport results pass schema validation before publication; semantic/quality approval still precedes bank/session persistence. Enrichment prompts now include technology and untrusted-content rules. The legacy exported session generator delegates to the same governed snapshot path instead of bypassing validation and limits.
- **Cancellation:** Disconnected custom/saved-session requests are checked before private session persistence. Frontend owner epochs and cancellation continue to suppress stale private results. Shared provider work can finish for other subscribers; disconnecting one client does not revoke another user's work. Transport cancellation cannot undo a provider charge or a database write that has already committed.

## Session lifecycle and security

Saved sessions now support create → practice → saved self-check progress → complete → history/resume. Question/answer snapshots are immutable through the model and the progress endpoints; progress is stored separately. Snapshots deduplicate questions and preserve structured answers, provenance, verification status, stable question IDs and content hashes. Existing historical snapshots are not rewritten.

- Session creation accepts `Idempotency-Key` or `idempotencyKey` (8–128 alphanumeric, underscore or hyphen characters). A unique partial `{userId, requestKey}` index and request fingerprint prevent duplicate saved sessions on retries and return 409 if a key is reused for a different request. Legacy callers without a key remain supported; they must adopt a key for retry idempotency. The browser keeps the same key after an uncertain creation failure. Custom question identities have owner-scoped unique request keys as an additional race barrier.
- `GET /api/interview-prep/sessions/:id` reads only the authenticated owner's session. `PATCH .../:id/progress` accepts `{expectedVersion, questionIndex, selfCheck}` where selfCheck is `review` or `comfortable`. `POST .../:id/complete` accepts `{expectedVersion}`. Each mutation validates ID, ownership, question bounds and version. Atomic compare-and-update returns 409 on conflicting writes. Identical completed/self-check retries do not increment the version again. Complete requires a self-check for every question; it does not require a favorable self-rating. Completed sessions reject further changes.
- Authentication retains HS256, issuer/audience verification, active-user and session-token checks. Body/query structures are rejected before normalization/providers. Missing/foreign sessions return the same 404. Error responses omit provider/database internals. The new handlers never accept user IDs, questions, answers, XP, skills or scores as updateable progress fields.
- The UI preserves its layout and cards, adds a saved-session completion button, locks completed self-checks, reports save errors, and reloads progress after conflicts. Existing transient practice remains available.

## Cross-module contracts

Missing evidence does not establish inability. Session personalization explicitly states that practice/completion does not establish verified ability or change readiness scores.

Progress/completion writes only `InterviewPrepSession`. They do not write proficiency, readiness, verified skills, XP or Sprint tasks. ## MongoDB query/index verification

Tests create fresh random fixture databases on a task-owned MongoDB 8.2 process bound to `127.0.0.1:27167`. They do not use application environment files or production credentials. The integration test no longer drops a database supplied through an environment URI; the launcher owns the ephemeral server's exact data files.

The baseline executionStats evidence is retained in [query-before.tap](query-before.tap). For a 10-row JavaScript page, the existing `topic_stable_page` examined 10 keys/10 documents; no pagination index change was justified. A filtered query used `topic_filtered_candidates` and examined 1 key/0 documents for the empty fixture bucket; that does not establish large-scale performance. Global text search examined 101 keys/202 documents to return 10 topic-scoped rows, demonstrating avoidable cross-topic work.

The text index alone changed to `{topicKey: 1, question: 'text', answer: 'text', tags: 'text'}`, named `topic_question_text`. Every production Interview catalog text caller supplies exact `topicKey` equality. Existing unique, compound and pagination indexes remain. The final executionStats output records the new plan and measurements below. Local fixture cardinality is not production capacity testing.

**Deployment gate:** MongoDB permits one text index per collection. An existing deployment must inventory and deliberately replace `question_text_answer_text_tags_text_topicKey_text` with `topic_question_text` using its approved index-maintenance procedure, then verify real query plans. Merely deploying this schema or calling `createIndexes()` against the old text index is insufficient. No production index was created/dropped here. Also deploy/verify the session partial unique index and coordinator `_id`/TTL indexes before enabling multi-worker traffic. Do not run broad `syncIndexes()` blindly.
